# 增量变更与一致性检查

## 增量分析

先将本次要求写成一条可观察差异：什么对象、哪个角色、原来如何、现在如何。区分属性、对象关系、权限、状态、动作或流转规则变化；有界面证据时，再核对展示与交互是否受影响。

已有模型或实现时读取相关部分；没有文档时，可将用户明确描述的旧规则作为基线。缺少旧规则时列为未知，不虚构前后差异。按以下关系扩展受影响范围，直到没有新增依赖：

对象/属性 → 写入动作 → 状态与关联约束 → 数据消费者 → 汇总/派生结果 → 样例与验证规则。已有页面、接口、规格或日志定义时，再核对其受影响部分。

输出变更表：

| 项目 | 原规则 | 新规则及依据 | 受影响对象/动作/数据 | 处理方式 | 验证 |
| --- | --- | --- | --- | --- | --- |

没有历史实现或运行环境时说明未知，不推测已改。用户授权实现时，将业务差异交给实现步骤；只要求分析时交付建议与规格，不改源码。

## 高价值检查

| 检查面 | 需要核对的问题 |
| --- | --- |
| 责任与边界 | 变更是否改变对象归属、处理责任或某个动作的适用范围？ |
| 角色权限 | 动作处理是否校验实际权限？其他组织能否读取草稿或编辑别人的资料？ |
| 状态可达 | 已通过却缺少必需决策？归档后仍可改？退回后没有继续入口？ |
| 材料归属 | 协作资料由谁填写、谁确认？同一材料是否被多个模块各存一份？ |
| 汇总口径 | 明细变动后汇总、数量和状态是否一致？部分处理是否错误影响全部？ |
| 数据版本 | 草稿是否泄漏给下游？重新提交读取新版本还是旧快照？ |
| 实例与配置 | 修改模板是否改变已在办实例？节点排序与分支目标是否一致？ |
| 操作后果 | 自动推送是否重复？撤回是否需要处理已经产生的下游任务？ |
| 前置条件 | 执行动作的对象是否具备必要条件及关联数据？异常样例是否有依据？ |
| 模型与证据 | 对象、属性、状态和动作是否同一口径？已有规格、样例或实现是否与已确认规则冲突？ |

变更影响核心任务、参与者责任或流程分支时，同步检查相关任务说明与流程图；只有视觉调整时不重建角色或流程。涉及界面时，另核对页面职责、菜单、字段、按钮、提示与相关业务规则的一致性。

## 评审输出

发现按业务影响排序，给出位置/证据、触发条件、错误结果、建议及受影响范围。区分已观察到的问题、仅规格层面的矛盾、尚未核实的风险。

没有发现问题时说明检查过的对象与资料、未核实的规则和运行行为，不把有限检查写成全系统无问题。

## 示例：提交后禁止修改

变更作用于某项目中各角色的资料填报，不扩散成所有产品的通用规则。

应同步检查：提交状态定义；编辑、新增子项、删除和上传等写入动作；保存与提交时的状态检查；聚合结果读取正式版本；历史草稿处理；是否存在明确授权的退回路径。已有页面、日志或规格时，再核对相关入口、记录和描述。

保留查看、预览和下载。没有业务依据时不自行增加撤回提交、管理员解锁或修订流程。未提交示例仍可填报，以便验证可编辑与锁定两条路径。

## 最小输出

- 本次变更的已确认规则及必要未决事项。
- 受影响对象、状态、动作和消费方；有相关界面时再列受影响页面。
- 模型或业务规格补丁，或明确的修改建议，遵循本次授权。
- 可观察的验证步骤与尚未验证的部分。

小型文案或间距调整若不影响语义，只核对相关入口即可，不要求完整动作矩阵。
