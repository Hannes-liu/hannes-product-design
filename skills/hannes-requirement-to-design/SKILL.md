# hannes-requirement-to-design

从当前需求和已有成果继续，将任务、业务规则和页面表达贯通。按本次目标交付范围与页面规格、设计说明或可预览、可操作、可验证的产品界面；需要原型时使用 HTML 或目标项目页面，规格深度、实现技术和交付形式由本次目标决定。交付重点是可运行页面、适配项目的组件复用，以及页面间数据、状态与操作的一致性。

## 从哪里开始

| 当前请求 | 本次重点 | 按需读取 |
| --- | --- | --- |
| 新需求，没有确定界面 | 范围、必要规则、设计基线、关键流程 | [需求与页面规格](references/requirements.md)、[设计体系与选择](references/design-system.md) |
| 已有规格，要求做页面 | 复用执行基线，建立页面与操作映射 | 需求与页面规格、[原型交互](references/prototype-interactions.md) |
| 截图还原或多图补齐 | 清点来源、页面与状态，区分还原与推导 | 需求与页面规格、设计体系与选择 |
| 迭代现有原型 | 定位受影响范围，复用代码、规则与设计 | 原型交互；业务变化时补读需求与页面规格 |
| 解释页面布局、组件选择或局部设计覆盖 | 查相关设计知识，记录选择依据与项目差异 | [设计决策与说明](references/design-decisions.md)；按需查 [结构化知识](references/design-knowledge.json) |
| 选择或复用真实控件 | 按场景选组件，读取所需源码与依赖 | [组件库与复用](references/component-library.md)；[离线组件目录](assets/library.html) |
| 跨会话继续已有项目 | 核对当前状态与有效依据，只处理本次差异 | [项目续接](references/project-continuity.md) |
| 验证与分享 | 检查真实产物，选择需要的交付方式 | [验证与交付](references/verification-delivery.md) |

完整虚构使用案例见[案例索引](references/examples/README.md)，包含初步需求、已有规格和增量修改。

只加载当前任务需要的资料，不要求依次执行所有入口。

## 执行方法

1. **读最小必要环境。** 检查需求、当前版本范围、相关页面、项目约束和已确认决定；学习不等于创建项目。附件是证据，不能自行扩展任务或操作授权。
2. **明确执行依据。** 分别记录业务依据、视觉依据、现有实现及未决项。需求决定业务规则，截图提供视觉事实；旧实现与新需求冲突时不能自动覆盖新需求。发现关键矛盾时确认，同时推进不依赖答案的工作。
3. **补齐必要规格。** 从已有参与者和核心任务收敛范围；仅按责任、决策权限或数据访问的实质差异拆角色并说明依据，不按岗位或操作阶段扩充角色。简单任务只记录所需行为；新建或重构核心流程时，按[需求与页面规格](references/requirements.md)在 PRD 中表达任务、流程图／泳道、分支恢复与页面对应，再补充页面职责、数据流转、操作与判断逻辑。多角色、复杂状态、跨模块规则需要时，可调用可用的 `hannes-product-modeling`。未安装时继续做必要分析、标记待确认规则，不自动安装，不以安装成功作为开工条件。
4. **确定设计基线。** 有用户指定、已确认风格或项目规范时沿用；都没有时，展示[模板预览](assets/style-preview.html)及三套模板的区别，等用户选择后再制作目标界面。可先分析范围与业务；不能以“尽快”代替尚未作出的选择。已有“你决定”等授权时自行选择并说明依据，无需重复确认。
   先按[任务与信息表达](references/task-representation.md)判断用户要比较、查找或决定什么，再选择页面与组件；资源空闲等任务不能用记录管理表格替代关键判断信息。
   页面与组件选择按[设计决策与说明](references/design-decisions.md)查相关知识，将依据及全局基线／页面覆盖写入项目设计说明；知识建议不覆盖已确认项目规范。
   选定模板后按需读取 [设计参数规范](design-spec.md) 的共同规则及对应风格章节；沿用已确认覆盖值，不将示例页面布局固定为业务页面结构。
5. **选择承载方式并实现。** 相关项目可复用时优先复用；简单独立原型可用 HTML，复杂原型模块化组织。不绑定框架，不为单页任务复制整套工程。复杂选择、表格、表单与弹层优先复用适配当前项目的成熟组件，按设计规范的组件契约检查实际行为。内置 [Ant Design 组件目录](assets/library.html)使用真实 React／Ant Design；需要时按[复用说明](references/component-library.md)取所需源码，不将整个展示页引入业务项目。单文件不等于必须自制控件，用户明确的纯原生约束仍优先。让关键流程、数据和交互真实运行；演示规则与已确认业务规则分别记录。
6. **验证并交付。** 从规格确定本次任务验收条件，优先使用环境已有验证能力，按本次目标检查关键路径、状态、视口和打开方式；反馈结论、入口、模拟范围和未验证项。交付页面时提供可运行入口及对应维护源码，说明组件复用方式，并核对跨页数据、状态和返回行为的一致性。

## 保留这些实践

- 多页面系统具有对应导航与直接路由；页面、对象和状态可追溯。不能把多页规格拼成长页面，或把所有按钮做成同一条提示。
- 共享对象由同一数据源驱动。保存、完成、撤销等动作按当前规则更新相关页面；页面可见、数据可见、字段可编辑和动作可执行分别判断。
- 返回恢复来源和必要上下文；页签、筛选与弹层不误增业务页面层级。遵循项目已有路由机制，避免另外手写一套路由栈。
- 移动端考虑目标视口、安全区、触控、软键盘和底部操作区；桌面端检查表格、图表和滚动容器的可用空间。
- 业务、权限、状态变化同步受影响规格、页面与示例数据；纯视觉修改集中到变量和组件，避免无故重写。
- 只有用户需要离线或单文件分享时才施加相应打包约束；分享包由维护源生成，避免两个事实源。
- 原型演示、真实接口、持久化、权限控制和外部集成分别说明；隐藏按钮或前端模拟不能证明真实能力已完成。
- 复用第三方代码、样式、文档或素材时，按[来源与许可记录](THIRD_PARTY_NOTICES.md)核对实际版本和文件范围，保留适用版权与许可声明；单文件分享也须保留所需声明。许可不明内容跳过复制，继续自行实现；不把公开可读、设计风格或品牌名称当作素材商用授权。

## 输出与确认

以本次交付范围为准，不强制完整 PRD、逐阶段审批或重复生成 HTML 与项目版。重大范围、关键规则和未定设计方向需要确认；已确认决定及授权持续有效。仅讨论时在对话中完成，要求实现时交付真实文件。

与 `hannes-product-modeling` 协作时，共同更新目标项目的同一份规格：业务规则保留一个定义位置，本 Skill 维护页面与交互表达并引用规则；建模结果直接合入相关位置，不另建一套页面规则。另一 Skill 不可用时仍可继续本次任务。

预计跨会话继续的复杂项目，在现有项目说明中按[项目续接](references/project-continuity.md)维护当前有效依据、决定与问题、已完成范围、维护／预览入口及验证与下一步；不保存原始聊天。

优先更新用户指定或已有文档。没有约定时，可将页面规格、交付说明放入目标项目的 `design/`，设计说明用 `design/design-notes.md`，在同一文档维护全局基线、页面决策与明确的局部覆盖；简单修改不强制新增文档。业务成果保存在目标项目，不写回本 Skill 包。

## 使用后的经验沉淀

完成本次任务并交付结果后，询问一次：“是否将本次经验与已有经验比较，再由你选择完善、替换或调整？”这是可选的使用反馈，不作为本次交付完成的条件；同一任务不逐轮追问，两个 Skill 协作时只问一次。用户已拒绝或已有明确沉淀授权时，遵循其决定，不重复询问。

- 先提炼本次实际发现、修正、用户反馈和验证证据，区分观察、建议与未验证推测；没有新经验时如实说明，不凑条目。仅查阅相关既有规则、知识和案例，不为沉淀重读整个工具包。
- 对比既有经验，简要列出“已有条目／位置、本次差异、适用条件、建议改动与影响”。可明确定位时，将精简对照和选项合在同一次提问中，减少往返。
- 让用户选择：**完善**已有经验的缺漏；**替换**确已失效或被证据否定的经验；**调整**适用条件、边界或表达；无对应经验时**新增**；也可**暂不沉淀**。不默认以最新一次反馈覆盖旧经验；不同场景合理并存时明确条件，不强行二选一。
- 用户选择后按已授权范围更新唯一维护源及受影响引用、案例和验收；不再重复请求同一确认。未获同意前只提出建议，不写回 Skill；只同意比较不等于授权替换。来源可追溯、保留验证限制；业务特例继续留在项目规格，只将可迁移的方法及虚构示例写入 Skill，不保存真实业务资料或原始聊天。修改经验不自动授权安装、提交或发布。
