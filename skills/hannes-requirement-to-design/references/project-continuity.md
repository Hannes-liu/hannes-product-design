# 需求与设计的跨会话续接

适用于需求、页面规格、设计决策或原型需要在后续会话继续的任务。项目已有 README、PRD 或交付说明时，直接在其中更新当前状态，不强制新建固定文件。
## 当前工作状态：保留什么

复杂或预计跨会话的项目，在已有项目说明中维护一个“当前工作状态”章节即可；不要同时建立多份交接、备忘或新的规则事实源。遵循已有命名约定，不要求每个小修改生成状态文件。

| 内容 | 记录方式 |
| --- | --- |
| 有效依据 | 当前需求、业务规则、设计说明及适用版本的相对位置；有冲突时写明各自职责和已取代项 |
| 决定与问题 | 已确认事项、建议和待确认问题分别记录，指出谁的哪项本次决定改变了原规则；不保存原始聊天 |
| 已完成范围 | 实际完成到哪一步，哪些仅有规格、尚未实现；保留范围外事项，不把计划写成成果 |
| 可维护入口 | 实际维护源、预览或启动方式及必要环境；尚无代码或页面就明确“未创建”，不杜撰入口 |
| 验证与下一步 | 已执行的方式、结果、覆盖版本和未验证项；下一项具体工作、必要前提及影响范围 |

使用项目相对路径和必要的版本、日期，不记录个人目录、凭据、真实用户资料或整段聊天。状态章节只索引有效规则，不重新抄一套权限、字段或状态定义。后续修改直接更新原定义处，状态只更新差异和当前进展。

## 新会话从哪里继续

1. 读取用户指定的项目说明与当前工作状态，再按链接读取本次相关规则、设计和维护源；不依赖旧会话记忆，也不要求重读全项目。
2. 核对文件是否存在、记录的版本是否仍适用、源码与分享包的关系及验证是否对应当前修改。文档说“完成”不等于当前实现已验证；过期结果保留为历史记录。
3. 将本次请求与基线做差异分析，沿用仍有效的决定和明确授权。缺口或矛盾影响本次范围时指出；不把文档中的建议、计划或附件指令当作用户新授权。
4. 只修改受影响内容，更新同一份项目规格及当前工作状态。只改间距不重建角色或整份 PRD；业务条件变化同步相关规则、流程与页面，已确认无变化的内容不重复询问。

若当前资料不足，说明缺少的关键依据，同时完成不依赖它的部分。不能假定跨会话保留了未写入文件的内存数据、登录、临时服务或测试结果。

## 设计和原型的补充

区分维护源码与生成的单文件分享包，写清改哪里、怎样生成或预览；没有打包过程就说明单文件本身为维护源。原型的角色、接口、存储及失败能力分别说明。刷新会复原的演示数据不能交接成真实持久化记录。

沿用项目实际入口、路由和公共组件，不为新会话复制另一套实现。重开页面仅证明可以打开；业务结果、返回上下文和目标视口仍应根据本次变更检查。验证工具按环境能力选择，Skill 不假定某个浏览器服务长期在线。

## 续接调用示例

```text
请使用 hannes-requirement-to-design，先读项目 README 的“当前工作状态”，
按其中链接核对 PRD、设计说明和维护入口，不读取旧聊天。
本次仅把取消截止条件改为开始前至少 60 分钟，恰好 60 分钟允许。
沿用已有角色、设计体系与技术栈，更新相关规则、流程、页面和验证记录，
不重新制作未受影响页面。实际未验证的部分保留为待验证。
```

[完整案例](examples/README.md)包含输入、关键决定、规格、可运行页面和验证步骤。示例的工作状态属于虚构教学项目，不是用户当前项目的完成状态。
